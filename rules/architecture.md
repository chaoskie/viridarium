# Architecture (`ARCH-*`)

**Enforces:** the structural skeleton - the stack lock, hexagonal layering, evolutionary bounded contexts, schema discipline at API boundaries, and how architectural decisions are recorded. Core ruleset for design work; REV-005 points the code-reviewer here. Implements [[00-constitution#PRIN-I Code Quality|PRIN-I]], [[00-constitution#PRIN-V Stack Lock-In|PRIN-V]].

---

### ARCH-001 — Stack lock
The locked stack. Adding or replacing any component requires a written amendment ([[00-constitution#PRIN-V Stack Lock-In|PRIN-V]]) recorded as an ADR (ARCH-010).

| Concern | Choice |
|---|---|
| Backend | **Python 3.12+ + FastAPI** |
| Persistence | **SQLAlchemy 2.x** ORM |
| DB engines | **SQLite** by default (zero-config self-hosting); **PostgreSQL** fully supported via `DATABASE_URL` |
| DB migrations | **Alembic** (must run on both SQLite and PostgreSQL) |
| Validation/schemas | **Pydantic v2** |
| Frontend | **React 18+ + TypeScript (strict)**, **Vite**, **Tailwind CSS** |
| E2E / acceptance | **Playwright** |
| API | **REST**, OpenAPI auto-generated by FastAPI, versioned under `/api/v1` (`API-*`) |
| CI runner | **GitHub Actions** (`CI-*`) |
| Auth | **None in v1** by design; trusted-network deployment (`SEC-003`) |
| Deferred | queues / events / user auth (amendment when needed) |

**Approved support dependencies** (added by amendment, pinned, pip-audit-scanned):
`python-multipart` (file upload / `multipart/form-data` parsing for FastAPI) - amendment ADR-010, 2026-06-09.

*Targets:* all agents.

### ARCH-002 — Hexagonal layering, dependencies inward
`adapters/infrastructure → application → domain`; dependencies point inward only. Python mapping:
- **domain/** - pure Python: entities, value objects, domain services, ports (Protocols/ABCs). **No FastAPI, no SQLAlchemy, no Pydantic, no HTTP, no I/O.**
- **application/** - use cases; depends only on domain types + ports.
- **adapters/inbound/web/** - FastAPI routers; the *only* place HTTP exists. No business logic in routers.
- **adapters/outbound/db/** - SQLAlchemy repositories + Alembic migrations; the *only* place persistence exists.
- **infrastructure/** - app wiring, dependency-injection composition root, settings/config loading.
*Targets:* developers, code-reviewer.

### ARCH-003 — Mechanical boundary enforcement
Layer and context boundaries are enforced **mechanically**, not just by review: **import-linter** contracts (domain imports no framework or outer layer; application depends only on domain; no cross-context imports). These run as a quality gate and are part of the QG-001 mechanical gate.
*Targets:* ci, code-reviewer, developers.

### ARCH-004 — Evolutionary bounded contexts (standing design duty)
The system starts as a **single hexagonal monolith**. Design work MUST **actively monitor for context pollution** and, when detected, propose carving a new bounded-context hexagon (evolving toward a modular monolith) via an ADR. Pollution signals include:
- one domain package serving ≥2 distinct business capabilities;
- use cases orchestrating unrelated aggregates;
- shared entities accumulating fields used by disjoint features;
- a change in capability A routinely forcing edits in capability B's code.
Each carved context gets its own full hexagon (ARCH-002) inside the same deployable.
*Targets:* design work (standing duty), spec-propose, retrospective.

### ARCH-005 — Context isolation (once ≥2 contexts exist)
Bounded contexts communicate **only through service interfaces** (ports/DI). Direct cross-context imports of entities, schemas, or repositories are forbidden. Dependency direction between contexts MUST be acyclic. Enforced via ARCH-003 tooling.
*Targets:* developers, code-reviewer.

### ARCH-006 — Read/write placement
Writes belong to the owning context. A read touching one context lives in that context. A read joining **2+ contexts** MUST live in a dedicated query module (no writes there).
*Targets:* developers.

### ARCH-007 — Three-layer schema pattern
1. **SQLAlchemy model** - single source of truth for persisted shape.
2. **Request schema** (Pydantic) - input validation, per API surface.
3. **Response schema** (Pydantic) - output filtering, per API surface; the response schema is a **security boundary** (no internal/PII fields leak).
Use cases return domain types, never response schemas; the HTTP layer (de)serializes.
*Targets:* developers, code-reviewer.

### ARCH-008 — Per-surface schema separation
Each API surface (e.g. public REST API vs any internal/ops surface) has its own request/response schemas. Cross-surface schema imports are forbidden.
*Targets:* developers.

### ARCH-009 — Anti-corruption at the boundary
External/third-party models (ingested REST payloads, vendor SDK types) are **mapped at the adapter boundary** and never leak inward. Domain and application layers see only our own types.
*Targets:* developers.

### ARCH-010 — ADRs for cross-cutting decisions
Cross-cutting or hard-to-reverse decisions are recorded as numbered ADRs: **Status / Context / Decision / Options considered / Rationale / Consequences**. Stack amendments (ARCH-001) and context carvings (ARCH-004) always get an ADR.
*Targets:* design work, retrospective.

### ARCH-011 — Dual-engine persistence discipline
Because both SQLite and PostgreSQL are supported (ARCH-001), persistence code and migrations MUST stay engine-portable: no engine-specific SQL or types on the critical path without a documented, tested fallback for the other engine. Alembic migrations MUST apply cleanly on both engines; batch mode is used where SQLite ALTER limitations require it. Engine-specific behavior is isolated in the outbound DB adapter.
*Targets:* developers, code-reviewer, ci.
